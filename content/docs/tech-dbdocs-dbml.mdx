DB設計は、**DBMLファイルを正本としてGitで管理し、dbdocsを閲覧・共有のためのビューとして使う**のがよい。

## DBMLとは

[DBML（Database Markup Language）](https://dbml.dbdiagram.io/)は、データベースの構造を記述するためのオープンソースのDSL。SQLのDDLよりも簡潔で、テーブル、カラム、インデックス、リレーション、設計意図をコードとして読みやすく残せる。

```dbml title="database.dbml"
Project example {
  database_type: 'PostgreSQL'
  Note: 'Example database'
}

Table users {
  id bigint [pk, increment]
  name varchar [not null]
  created_at timestamp [not null]
}

Table posts {
  id bigint [pk, increment]
  user_id bigint [not null]
  title varchar [not null]
  created_at timestamp [not null]
}

Ref: users.id < posts.user_id
```

## なぜDBMLファイルをGit管理するか

ER図だけを画像やWebサービス上で管理すると、変更理由や差分を追いにくい。DBMLをリポジトリに置けば、通常のコードと同じようにPull Requestでレビューでき、誰が・いつ・なぜ変更したかを履歴として残せる。

ここで重要なのは、dbdocs上の表示ではなく、リポジトリ内の`.dbml`ファイルを正本にすること。ツールを変更しても設計データが残り、アプリケーションやマイグレーションの変更と同じ単位でレビューできる。

## dbdocsの役割

[dbdocs](https://dbdocs.io/)は、DBMLからWeb上のデータベースドキュメントを生成するサービス。テーブル定義やリレーションを、コードを直接読まない人にも見やすい形で共有できる。

```bash
npm install -g dbdocs
dbdocs login
dbdocs build ./docs/database.dbml --project example
```

GitHub ActionsなどのCIから`dbdocs build`を実行すれば、mainブランチへマージされたDBMLを自動で公開できる。アクセストークンは`DBDOCS_TOKEN`としてSecretsに保存し、リポジトリにはコミットしない。

## 運用

プロジェクトごとにDBMLファイルを作り、そのリポジトリで管理する。既存DBから始める場合は、[DBML CLI](https://dbml.dbdiagram.io/cli/)の`db2dbml`でデータベースから、または`sql2dbml`でDDLから初期DBMLを生成できる（`db2dbml`はdbdocs CLIにも含まれる）。

## 注意点

DBMLは設計とドキュメントの正本であり、マイグレーション実行そのものの代替ではない。実DBへの変更は、利用中のマイグレーションツールで管理する。

また、dbdocsのプロジェクトは作成時の公開範囲を必ず確認する。スキーマには内部情報が含まれるため、公開できないDBではパスワード保護またはPrivate設定を使う。
